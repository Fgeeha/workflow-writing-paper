# План: конвейер написания научных статей с пулом языковых моделей

Версия плана: 2026-10-31. Кода пока нет; этот документ — техническое задание на v0.1–v0.4.

## 1. Назначение и границы

Приложение помогает исследователю довести научную новизну до статьи, а серию статей —
до контуров диссертации. Автор вводит формулировку новизны; дальше цепочка агентов на
языковых моделях разворачивает её в исследовательские вопросы, план экспериментов,
контур и черновик статьи. Каждый результат работы — артефакт в файловой системе; каждый
артефакт перед принятием проверяют модели других семейств, а принимает его человек.

Что приложение делает:

- ведёт проекты-статьи со стадиями и артефактами, показывает текущее состояние в веб-интерфейсе;
- держит пул провайдеров моделей (локальные и облачные), назначает модели на роли;
- сравнивает модели на эталонных задачах по каждой роли и рекомендует лучшую;
- запускает зарегистрированные сценарии экспериментов и складывает числа в реестр результатов;
- индексирует литературу пользователя и даёт агентам ссылаться только на неё;
- проверяет артефакты судьями из других семейств моделей и детерминированными проверками.

Что приложение не делает:

- не пишет научные утверждения без одобрения автора: любой текст — черновик до нажатия «принять»;
- не придумывает эксперименты и не запускает произвольный код: только сценарии, которые зарегистрировал человек;
- не публикует и не отправляет ничего наружу: ни `git push`, ни писем в редакции;
- не хранит ключи в репозитории и не зависит от конкретной машины, предметной области или специальности.

## 2. Принципы

1. **Переносимость.** Клон репозитория плюс `uv` — и приложение работает у другого учёного с его
   проблемой, литературой и журналами. Всё предметное лежит в данных (`defaults/` и `workspace/`),
   а не в коде.
2. **Человек в контуре.** Граница стадий и любой платный вызов выше лимита — точка остановки до
   решения автора. Внутри стадии агенты работают автономно.
3. **Числа только из реестра.** В тексте статьи не может появиться число, которого нет в
   `results.json` проекта. Проверка детерминированная, без модели.
4. **Чужие семейства проверяют.** Семейство модели, создавшей артефакт, не участвует в его проверке.
5. **Детерминированное — где можно.** Перекрёстные ссылки, числа, список литературы, объёмы
   проверяются кодом; модели достаётся то, что кодом не проверить.
6. **Минимум зависимостей.** Стандартная библиотека, FastAPI, Jinja2, HTMX, pymupdf, PyYAML.
   Без фреймворков оркестрации, без torch, без сборки фронтенда.
7. **Воспроизводимость.** Каждый вызов модели записан целиком: промпт, ответ, модель, параметры,
   токены, время, стоимость.

## 3. Принятые решения

| # | Вопрос | Решение |
|---|---|---|
| 1 | Наработки стенда рецензирования рукописей | Адаптеры провайдеров, рубрика и голосование копируются в собственный модуль; внешних зависимостей от того репозитория нет |
| 2 | Пользователи | Один пользователь, `127.0.0.1`, без аутентификации |

| 6 | Выбор моделей | Эталонные задачи по ролям + A/B на живых задачах; стенд рекомендует, назначает человек |

| 8 | Темп | Фоновый воркер в процессе сервера; гейты на границах стадий и по бюджету |
| 9 | Локальный провайдер | ollama по умолчанию; OpenAI-совместимый сервер как включаемый профиль |

| 12 | Литература | Импорт PDF и BibTeX, поиск SQLite FTS5; эмбеддинги через ollama как включаемый режим; OpenAlex как необязательный внешний поиск |
| 13 | Шаблоны проектов | «экспериментальная», «обзор», «теоретическая»; стадии помечены обязательными или нет |
| 14 | Язык | Интерфейс: русский по умолчанию, английский вторым файлом строк; промпты в обоих языках по языку статьи; код и идентификаторы — английский |
| 15 | Лицензия | MIT; репозиторий приватный до v0.1 |
| 16 | Имя | Пакет `workflow_writing_paper`, команда `wwp` |
| 17 | Версионирование артефактов | Коммит в git проекта при одобрении (без пуша), отклонённые версии в `history/` |
| 18 | Стиль автора | `style/samples/` и `style/banned_phrases.txt` в проекте читаются в промпт редактора |
| 19 | Экспорт | Только через внешний pandoc, если установлен |
| 20 | Порядок внедрения | Провайдеры и стенд → проекты и стадии → литература → эксперименты |
| 21 | Workbench-аналоги (Claude Science, K-Dense BYOK, Rosalind, Discovery) | Вне конвейера: источник данных для `results.json` и ориентир для стенда. Адаптер только при безголовом API с текстом, токенами и стоимостью; K-Dense BYOK — кандидат на проверку перед v0.3. Анализ — [ANALOGS.md](ANALOGS.md) |

## 4. Архитектура

```
┌──────────────────────────────── wwp serve (один процесс) ────────────────────────────────┐
│                                                                                           │
│  web/            FastAPI + Jinja2 + HTMX: проекты, артефакты, гейты, пул, стенд, журнал   │
│      │                                                                                    │
│  core/engine     граф стадий, очередь задач (SQLite), фоновый воркер (asyncio)            │
│      │                                                                                    │
│  ┌───┴──────────┬──────────────┬──────────────┬──────────────┬──────────────┐             │
│  roles/        review/        eval/          library/       experiments/   registry/      │
│  промпты ролей судьи,         эталонные      PDF→FTS5,      сценарии,      results.json, │
│  и сборка      рубрики,       задачи,        BibTeX,        subprocess/    проверка чисел│
│  контекста     голосование    таблица        OpenAlex       SSH, парсер                  │
│  └───┬──────────┴──────────────┴──────────────┴──────────────┴──────────────┘             │
│      │                                                                                    │
│  providers/     ollama · openai-compatible · openrouter · codex-cli · opencode-cli ·      │
│                 claude-cli · generic-cli · gigachat · fake (тесты)                         │
│      │                                                                                    │
│  storage/       SQLite (индекс, очередь, журнал вызовов) + файлы workspace/ и проекта     │
└───────────────────────────────────────────────────────────────────────────────────────────┘
```

Единый интерфейс провайдера:

```python
class Provider(Protocol):
    id: str
    family: str          # qwen, gemma, openai, anthropic, gigachat, ...
    def complete(self, messages: list[Message], *, json_schema: dict | None = None,
                 max_tokens: int, temperature: float, seed: int | None) -> Completion
```

`Completion` несёт текст, разобранный JSON (если просили схему), счётчики токенов, длительность
и стоимость по таблице цен из `providers.yaml`. Если модель не поддерживает структурированный
вывод, адаптер извлекает JSON из текста и повторяет запрос до двух раз.

Параллелизм: вызовы к GPU-провайдерам (`gpu: true`) выполняются строго по одному, облачные —
до `max_parallel` из конфигурации. Два GPU-провайдера, несовместимых по памяти, объявляются
в одной группе `exclusive_group`, и воркер не запускает их одновременно.

### 5.2. Рабочая папка `workspace/`

Путь по умолчанию — `./workspace`, переопределяется флагом `--workspace` или переменной
`WWP_WORKSPACE`. Переезд на другую машину — копирование одной папки.

```
workspace/
├── env                    # KEY=VALUE, ключи провайдеров; читается при старте
├── providers.yaml         # пул провайдеров, назначение моделей на роли, цены
├── prompts/               # переопределения defaults/prompts (копия при init)
├── rubrics/
├── journals/
├── templates/
├── eval/
│   ├── tasks/<role>/*.yaml
│   └── runs/<timestamp>/   # ответы, оценки судей, оценки человека
├── library/
│   ├── pdf/               # импортированные файлы
│   ├── refs.bib           # объединённый BibTeX
│   └── index.sqlite       # извлечённый текст + FTS5 (+ эмбеддинги при включении)
├── projects/<slug>/       # проекты по умолчанию (внешние — по ссылке в индексе)
└── wwp.sqlite             # индекс проектов, очередь задач, журнал вызовов, A/B-выборы
```

### 5.3. Проект-статья

Каталог проекта может быть внутри `workspace/projects/` или где угодно (например, существующий
git-репозиторий статьи). Приложение работает одинаково.

```
<project>/
├── paper-workflow.yaml    # манифест
├── results.json           # реестр результатов — единственный источник чисел
├── artifacts/
│   ├── novelty.md
│   ├── literature.md
│   ├── experiment_plan.md
│   ├── draft.md           # контур + черновик, растёт по разделам
│   ├── history/<artifact>.v<N>.md
│   └── reviews/<artifact>.v<N>.<judge>.json
├── calls/<timestamp>-<role>-<model>.json   # полные записи вызовов моделей
├── style/
│   ├── samples/*.md       # тексты автора для редактора
│   └── banned_phrases.txt
└── scenarios/             # зарегистрированные сценарии экспериментов (при наличии)
```

## 6. Форматы файлов

### 6.1. `providers.yaml`

```yaml
providers:
  - id: ollama-gemma4-12b
    kind: ollama
    family: gemma
    model: gemma4:12b
    url: http://127.0.0.1:11434
    gpu: true
    exclusive_group: local-gpu
    num_ctx: 32768
  - id: openai-compat-local
    kind: openai
    family: qwen
    model: Qwen3.6-35B-A3B-NVFP4
    url: http://127.0.0.1:1919/v1
    gpu: true
    exclusive_group: local-gpu
    enabled: false
    params: {temperature: 0.7, top_p: 0.8, top_k: 20, presence_penalty: 1.0}
  - id: claude
    kind: claude-cli
    family: anthropic
    model: sonnet
    price: {input_per_1m: 0, output_per_1m: 0}   # подписка CLI
  - id: codex
    kind: codex-cli
    family: openai
    model: default
    price: {input_per_1m: 0, output_per_1m: 0}
  - id: openrouter-x
    kind: openai
    family: minimax
    model: minimax/minimax-m3
    url: https://openrouter.ai/api/v1
    api_key_env: OPENROUTER_API_KEY
    max_parallel: 2
    price: {input_per_1m: 0.3, output_per_1m: 1.2}

roles:                       # назначение по умолчанию; проект может переопределить
  ideator: codex
  critic: ollama-gemma4-12b
  literature_scout: ollama-gemma4-12b
  experiment_planner: codex
  section_writer: codex
  editor: ollama-gemma4-12b
  judge: [ollama-gemma4-12b, openrouter-x]

profiles:                    # быстрые переключатели в интерфейсе
  local-only: {ideator: ollama-gemma4-12b, section_writer: ollama-gemma4-12b}
  quality:    {ideator: codex, section_writer: codex}
```

Поле `kind` — адаптер: `ollama`, `openai`, `codex-cli`, `opencode-cli`, `claude-cli`, `generic-cli` (любой консольный агент, команда и разбор вывода из конфига),
`gigachat`, `fake`. Поле `family` — семейство для правила «чужие проверяют».

### 6.2. `paper-workflow.yaml`

```yaml
name: edge-plant-disease
title: ""                      # заполняется на стадии контура
language: ru                   # язык статьи и промптов
template: experimental         # имя из templates/
journal: generic               # имя из journals/
chapter: 4                     # привязка к главе диссертации (необязательно)
budget: {tokens: 5_000_000, usd: 20}
review: {judges: 2, threshold: null, auto_iterations: 2}   # threshold null — порог из рубрики
roles: {}                      # переопределения providers.yaml:roles
stages:                        # копируется из шаблона, можно править
  - {id: novelty,         required: true}
  - {id: literature,      required: true}
  - {id: experiment_plan, required: true}
  - {id: experiments,     required: false}
  - {id: draft,           required: true}
  - {id: review,          required: true}
  - {id: assembly,        required: true}
scenarios:
  - id: bench-c6
    cwd: ./                    # относительно проекта или абсолютный
    host: local                # local | ssh:<alias>
    command: ["python", "run_bench.py", "--config", "c6.yaml"]
    results: ["out/metrics.json"]
    mapping:                   # путь в файле результатов → ключ реестра
      "$.latency_ms.p50": latency_p50_ms
      "$.ram_mb.peak":    peak_ram_mb
```

### 6.3. `results.json`

```json
{
  "latency_p50_ms": {"value": 103.32, "unit": "ms", "source": "bench-c6", "run": "2026-10-31T12:00:00", "seed": 42},
  "f1_zero_shot":   {"value": 0.207,  "unit": "",   "source": "manual",   "note": "внесено автором", "run": null}
}
```

Пишут в реестр только парсер сценариев и форма ручного ввода. Проверка чисел: каждое число
в `draft.md` вне кода и формул должно совпадать (с учётом округления, объявленного в профиле
журнала) с каким-либо `value` реестра либо быть помечено `{pending}`.

### 6.4. Артефакт

Markdown с заголовком YAML:

```yaml
---
type: novelty
version: 3
status: draft | in_review | approved | rejected
created_by: {role: ideator, provider: codex, family: openai, call: calls/2026-10-31T12-00-00-ideator-codex.json}
reviews: [artifacts/reviews/novelty.v3.ollama-gemma4-12b.json, artifacts/reviews/novelty.v3.openrouter-x.json]
approved_by: human
approved_at: 2026-10-31T13:00:00
override_reason: null
chapter: 4
source: <исходный ввод автора; судьи видят его как подтверждённые материалы>
review_summary: {accepted: false, threshold: 7.0, min_overall: 6.98, blockers: 0, errors: []}
---
```

### 6.5. Ответ судьи

```json
{
  "artifact": "novelty.v3",
  "judge": {"provider": "ollama-gemma4-12b", "family": "gemma"},
  "scores": {"C1": 8, "C2": 6, "C3": 7},
  "overall": 7.0,
  "verdict": "accept | minor | major | reject",
  "blockers": [{"line": 42, "quote": "…", "issue": "…", "check": "grep 'F1 = 0.65' draft.md"}],
  "comments": ["…"]
}
```

Критерии `C*` берутся из рубрики типа артефакта; рубрика задаёт названия, веса и порог.

### 6.6. Эталонная задача стенда

```yaml
role: critic
id: critic-001
language: ru
input: |
  <артефакт или фрагмент, на который должна отреагировать роль>
expected:                       # что должен содержать хороший ответ
  must_mention: ["отсутствие базовой линии", "размер выборки"]
  must_not: ["общие слова без привязки к тексту"]
rubric: rubrics/critic.md
```

### 6.7. Профиль журнала

```yaml
id: generic
language: ru
sections: [Введение, Постановка задачи, Метод, Эксперимент, Обсуждение, Заключение]
limits: {abstract_words: 250, body_pages: 12, references_min: 15}
citation_style: gost-2008 | apa | ieee
numbers: {decimal_separator: ",", rounding: 2}
```

## 7. Стадии и роли

| Стадия | Роли | Вход | Выход | Детерминированные проверки |
|---|---|---|---|---|
| `novelty` | ideator → critic → ideator (ответ на критику) | абзац новизны от автора | `novelty.md`: 3–5 формулировок, исследовательские вопросы, гипотезы с критерием опровержения, список утверждений с указанием, чем подтверждается каждое, возражения и ответы, целевые журналы | структура разделов |
| `literature` | literature_scout, critic | `novelty.md`, индекс библиотеки | `literature.md`: позиционирование, карта близких работ, оценка новизны относительно найденного, пробелы | каждая ссылка есть в `refs.bib` или найдена по DOI; «выдуманная» ссылка — блокер |
| `experiment_plan` | experiment_planner, critic | `novelty.md`, `literature.md` | `experiment_plan.md`: для каждого утверждения — эксперимент, метрика, базовые линии, число прогонов, ожидаемый ключ реестра | каждое утверждение покрыто; каждый ключ объявлен |
| `experiments` | — (воркер), human | сценарии из манифеста | записи в `results.json`, логи запусков | парсер по `mapping`; расхождение с уже записанным значением — остановка и вопрос автору |
| `draft` | section_writer, editor | все артефакты, `results.json`, профиль журнала, `style/` | `draft.md`, растёт по разделам; каждый раздел — отдельная задача с собственной проверкой | числа ↔ реестр; ссылки ↔ библиотека; перекрёстные ссылки на таблицы и рисунки; лимиты журнала; запрещённые фразы |
| `review` | judge × N | `draft.md` целиком | отчёт: оценки, голосование вердиктов, блокеры с привязкой | пересечение блокеров разных судей выносится первым |
| `assembly` | — | одобренный `draft.md` | `paper.md` + при наличии pandoc `paper.docx` / `paper.pdf` | сборка проходит без ошибок |

Правила движения:

- стадия завершается только одобрением автора всех её артефактов;
- возврат возможен на любую предыдущую стадию; зависимые артефакты получают статус `stale` и
  видны в интерфейсе как требующие пересмотра;
- необязательные стадии шаблона можно пропустить одной кнопкой с записью причины.

Каждая роль получает контекст, собранный кодом: системный промпт роли из `prompts/<lang>/<role>.md`,
профиль журнала, нужные артефакты, выдержки из библиотеки (только найденные через FTS5),
актуальный реестр результатов. Роль не видит того, что ей не положено: например, `section_writer`
не получает сырые логи экспериментов, только реестр.

## 8. Проверка семействами

Алгоритм для артефакта версии `v`:

1. Определить семейство автора артефакта `F_author`.
2. Выбрать `N` судей (по умолчанию 2) из назначенных на роль `judge`, семейства которых
   различны и не равны `F_author`. Если судей не хватает — задача ждёт и показывает причину.
3. Каждому судье — рубрика типа артефакта, артефакт, нужный контекст (реестр, библиография).
4. Собрать JSON-ответы; детерминированные проверки добавить как судью `checker` с весом блокера.
5. Решение: принято к одобрению, если `min(overall) >= threshold` и блокеров нет.
   Иначе артефакт отправляется роли-автору на правку с объединённым списком блокеров
   (не более двух автоматических итераций, дальше — человек).
6. Автор видит отчёт и выбирает: одобрить, одобрить с override (с причиной), вернуть на правку,
   отклонить.

Стоимость проверки показана заранее по таблице цен; если она превышает остаток бюджета —
остановка.

## 9. Стенд сравнения моделей

Цель — ответить на вопрос «какую модель поставить на роль X». Устройство:

- задачи в `workspace/eval/tasks/<role>/`, поставляются 2–3 обезличенных на роль; любой
  одобренный артефакт можно сохранить как задачу кнопкой «в эталоны»;
- прогон `wwp bench --role critic --providers a,b,c` или из интерфейса: каждая модель решает
  каждую задачу, ответы оценивают два судьи других семейств по рубрике роли, автор ставит
  оценку 1–5;
- живые A/B: при создании артефакта можно запросить две модели; выбор автора записывается;
- итог — таблица роль × модель: медиана оценки судей, медиана оценки автора, доля побед в A/B,
  медианное время, стоимость на задачу. Рекомендация — лучшая по оценке автора, при равенстве —
  по стоимости. Назначение на роль остаётся за человеком.

## 10. Эксперименты

- Сценарий регистрирует человек в манифесте или через форму; агент `experiment_planner` может
  предложить заготовку сценария, но до подтверждения она не исполняется.
- Запуск: `host: local` — `subprocess` с таймаутом и записью stdout/stderr;
  `host: ssh:<alias>` — `ssh <alias> cd <cwd> && <command>`, результаты забираются `scp`.
  Никаких специфичных для машины путей в коде, всё из манифеста.
- Парсер: `mapping` указывает путь JSONPath (для JSON) или `столбец@строка` (для CSV) → ключ
  реестра. При регистрации сценария модель может один раз предложить `mapping` по примеру файла;
  человек подтверждает.
- Конфликт: если ключ уже есть и значение расходится больше объявленной точности — запись не
  производится, задача останавливается с вопросом автору (старое значение, новое, разница).
- Воспроизводимость: в запись реестра входит время запуска, `seed` (если сценарий его объявляет),
  хэш команды и версия git в `cwd`, если это репозиторий.

## 11. Литература

- Импорт: папка PDF и файлы `.bib`. Текст извлекается pymupdf, режется на фрагменты по
  ~1000 символов с перекрытием, пишется в `library/index.sqlite` с FTS5. Запись BibTeX
  связывается с PDF по DOI или по нормализованному заголовку.
- Поиск: FTS5 с ранжированием BM25. Включаемый режим — эмбеддинги через ollama
  (`nomic-embed-text` или другой из конфига), поверх FTS5 как переранжирование.
- Внешний поиск: OpenAlex (без ключа) по запросу `literature_scout`; найденное попадает в
  `refs.bib` только после подтверждения автора.
- Правило цитирования: в артефактах допустимы только ключи из `refs.bib`. Проверка `checker`
  помечает любой иной ключ блокером. Это закрывает выдуманные ссылки без участия модели.

## 12. Веб-интерфейс

Серверный рендер, HTMX для частичных обновлений, без сборки фронтенда. Страницы:

| Страница | Содержимое |
|---|---|
| Главная | ожидающие решения автора: гейты, артефакты на одобрении, остановки по бюджету и конфликтам реестра |
| Проекты | список, создание из шаблона, привязка внешнего каталога |
| Проект | лента стадий с состоянием, артефакты по стадиям, бюджет, кнопки запуска стадии / возврата |
| Артефакт | текст, diff с предыдущей версией, отчёты судей с блокерами (переход к строке), действия одобрить / override / вернуть / отклонить / в эталоны / перепроверить судьями |
| Реестр результатов | таблица ключей, источники, ручной ввод, конфликты |
| Библиотека | импорт, список записей, поиск, предложенные OpenAlex-находки на подтверждение |
| Пул моделей | провайдеры, доступность (пинг), назначение на роли, профили |
| Стенд | задачи, запуск сравнения, таблица роль × модель, оценка автора |
| Журнал вызовов | все вызовы с фильтрами, полный промпт и ответ, стоимость |
| Настройки | промпты, рубрики, журналы, шаблоны — редактирование как текст |

## 13. CLI

```
wwp init [--workspace PATH]           создать workspace из defaults
wwp serve [--host 127.0.0.1 --port 8765]
wwp new <slug> --template experimental [--path /external/dir]
wwp run <slug> <stage>                поставить стадию в очередь
wwp bench --role <role> [--providers a,b]
wwp check <slug>                      только детерминированные проверки
wwp review <slug> [artifact]          перепроверить артефакт судьями без перегенерации
wwp export <slug> [--to docx|pdf]     через pandoc
wwp reindex                           пересобрать wwp.sqlite из файлов
wwp gc [--older-than 90d]             очистка журнала вызовов и истории
```

## 14. Таблицы SQLite (`wwp.sqlite`)

- `projects(slug, path, template, created_at)`;
- `tasks(id, project, stage, role, status, payload, created_at, started_at, finished_at, error)`;
- `calls(id, project, task, role, provider, family, prompt_path, tokens_in, tokens_out, duration_ms, cost_usd, created_at)`;
- `approvals(id, project, artifact, version, decision, override_reason, created_at)`;
- `ab_choices(id, project, artifact, provider_a, provider_b, chosen, created_at)`;
- `bench_runs(id, role, task, provider, judge_scores, human_score, duration_ms, cost_usd, created_at)`.

Файлы остаются первичны: SQLite можно пересобрать командой `wwp reindex` из содержимого
`workspace/` и проектов.

## 17. Риски

| Риск | Мера |
|---|---|
| Малые локальные модели не держат JSON-схему | извлечение JSON из текста, до двух повторов, затем задача помечается ошибкой с текстом ответа |
| Судьи одного семейства под разными именами (дистилляты) | поле `family` задаёт человек; в документации — список известных совпадений |
| Перерасход на облачных моделях | бюджет проекта, предварительная оценка стоимости проверки, остановка |
| Число «просочилось» в текст через формулу или таблицу | проверка чисел работает по всему markdown, кроме блоков кода; формулы проверяются отдельно по объявленным переменным |
| Проект привязан к внешнему каталогу, который переехал | индекс хранит путь; при отсутствии — статус `missing` и кнопка «указать новый путь» |
| Два GPU-сервера одновременно | `exclusive_group` в воркере |
| Модель узнаёт свои формулировки при проверке | правило семейств плюс запись `family` автора в артефакте |
